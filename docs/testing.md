# Testing

The three layers of testing, what each one catches, and what a
contribution owes. Golden notebooks verify code; evals verify the
agent's scientific judgment; runtime qualification verifies that a
release installs and behaves on each runtime it claims. The rules are
the specification's verification and evals layers
(docs/SPECIFICATION.md) and its runtime section.

| Layer | Tests | Instrument | Cadence |
|---|---|---|---|
| Golden notebooks (`verification/`) | code paths and expected results | marimo, headless, nonzero exit on failure | every pull request (CI) |
| Evals (`evals/`, or the capability's declared eval repository) | agent scientific judgment | cases in the schema below; seed-graded by hand, then the shared runner in the `evals` repository at N=20 | the seed pass on each new case; the runner per release |
| Runtime qualification (`.osp/qualification/`) | install, discovery, invocation, resolution, gates and PROVE on each runtime | build-kit's `scripts/qualify.py`: headless on Claude Code, by checklist elsewhere | every release candidate |

Behavior prompts (`docs/prompts/behavior/`) are the bridge: acceptance
tests captured verbatim, rerunnable after any skill edit, and the seed
corpus for eval cases. The layers feed each other, and each has caught
a real error the others would have missed:

- A behavior test found a transport recipe reporting a
  full-latitude-circle number where the observations it was compared
  against covered only the Atlantic: a scope mismatch that made the
  result silently wrong. Every number in a recipe now states its basin
  scope.
- A golden notebook falsified two assumed closure tolerances by
  measuring the actual residual (float32 quantization had made a
  relative criterion meaningless). Recipes now record the measured
  tolerance with its headroom, never a guess.
- The knowledge-linter caught two skills that still routed around a
  newly ingested gotcha, so the fact was documented but not yet acted
  on.

Testing here is not a gate at the end; it is the mechanism by which
the knowledge layer corrects itself.

## Golden notebooks

A workflow skill that encodes a computation is not done until its
marimo notebook in `verification/` runs green headless: `uv run
verification/<skill>.py` (PEP 723 inline dependencies, so it resolves
on any machine), nonzero exit on an assertion failure. CI runs every
notebook in the directory on each pull request; the plugin gate's
`check_script_deps.py` confirms each script declares what it imports.

- **Assert against recipe concepts, not constants you invent.** The
  notebook mirrors the recipe's expected values and says so; when a
  recomputation drifts from a recorded anchor, the golden fails and
  someone learns something. That is the point.
- **Measure tolerances before asserting them.** The criterion states
  what was measured, on what, and the headroom (the lesson above). A
  golden's own sanity assertions should be strong enough to catch a
  mis-built fixture.
- **Fixtures.** Synthetic fixtures are generated by a committed script
  with a fixed seed and never committed as artifacts; real-data
  fixtures are scripted, cached subsets, never committed above about
  5 MB and never through Git LFS; every `fixtures/` directory carries a
  provenance README recording each file's source, version, license or
  public-domain status, and the reference numbers.
- **Design fixtures with detectors built in.** The core temperature
  fixture makes an unweighted mean wrong by 6.7 K by construction, so
  the classic mistake cannot pass silently.
- **Pointwise versus domain-integrated closure.** Pointwise closure
  holds on any spatial subset (tile interiors need no seam operators);
  domain-integrated closure only on closed domains. Budget goldens
  assert pointwise on subsets.
- **Scope.** Goldens cover skills that encode a deterministic recipe
  (loaders, analyses, budgets, transport, the report pipeline). Pure
  orchestration skills (start, discover-data) are exercised by the
  conversational tests of runtime qualification instead.
- **CI security.** Golden workflows run on `pull_request` with no
  repository secrets; action versions are pinned by SHA.
- **marimo notes.** Constants live inside cells (module-level globals
  are not in the cell graph); no hidden state; `app.run()` under
  `__main__`.

An attested computation is a different object from a golden: a golden
tests the organization's own code in its own CI, while an attester
verifies anyone's run from the receipt they hand over. The reference
computation and its attester in `verification/` are what the `prove`
and `receipt` qualification tests run.

## Eval cases

Evals test agent scientific judgment with the capability installed:
does the agent apply area weighting, refuse a budget on regridded data,
surface the cal/val gotcha, report uncertainty? They are a quality and
regression instrument for this system (skill edits, knowledge updates,
model versions), not a model leaderboard.

**Where cases live.** A capability's cases have one home: its own
`evals/` beside `verification/`, versioned with the skills and
knowledge they test (core, hydrology), or an eval repository the
capability declares as their home. The ocean cases live in
`agent-evals` under `ecco/cases/`; ocean-science carries no copy, and a
case there names the ocean-science skills it exercises in `targets`. A
regression fixture that guards a capability's own artifact (a briefing's
receipt values) stays with the capability under
`verification/fixtures/`. This section is the one place the case schema
is documented; each `evals/SCHEMA.md` points here.

**Case types.**

- `gotcha-avoidance`: one per high-severity gotcha, mandatory; the
  gotcha's `eval_case` field names it. Does the agent surface and act
  on the trap unprompted?
- `rejection`: the hard refusals and gates hold (native-grid refusal,
  the volume gate).
- `methodology`: the correct method is chosen (area weighting, trend
  method, an uncertainty statement present); core's cases are of this
  type.
- `recipe-fidelity`: an end-to-end result lands inside the recipe
  concept's expected range and spread.

**Fields.**

```yaml
id: native-grid-refusal        # matches the gotcha's eval_case field
type: rejection                # one of the four types above
targets: [ocean-budget]        # the skills the case exercises ([] if none)
concept_basis: [knowledge/podaac/gotchas/ecco-native-vs-regridded.md]   # eval repositories: the signed concepts graded against, by bundle path, pinned to a provider commit
prompt: >                      # verbatim; no coaching on the tested behavior
  ...
fixtures: [verification/fixtures/...]   # empty list if none needed
graders:
  - programmatic: <checker id>          # transcript or output predicate, implemented by the shared runner
  - rubric: <rubric file>               # the rubric judge
trials: 5                      # seed runs; 20 under the shared runner
pass_threshold: 0.8
notes: >                       # grading guidance for the manual seed pass
  ...
```

**Writing a case.**

- The prompt states the task, never the tested behavior. Naming the
  expected behavior invalidates the case; the behavior prompts follow
  the same rule.
- Blind what must stay blind: fixtures with planted defects get neutral
  filenames, away from any documentation naming the defects.
- `graders` name a programmatic predicate, implemented by the shared
  runner in the `evals` repository, and a rubric file for the judge.
- `trials: 5` for the seed pass; the runner uses 20 and reports
  binomial confidence intervals. We apply our own uncertainty rule to
  ourselves.
- `notes` carry the manual grading guidance: what passes, what partial
  compliance looks like, and any recorded manual precursor.

**Seed grading.** One manual run per case on Claude Code, rubric-graded
by hand into the seed record (`RESULTS-seed.md` in a capability's
`evals/`; a results entry in an eval repository) with the model version
and date beside every grade. Reuse a recorded transcript only when its
prompt matches the case verbatim. Record failures honestly: the first
seed pass logged a real one (the house uncertainty rule not firing on
an uncoached computation prompt), and that finding is the seed's chief
value.

**The ablation.** The headline experiment runs the gotcha-avoidance
suite with the knowledge bundle installed and with it removed, same
model, same N, and reports the trap-hit-rate delta with intervals: the
quantitative evidence for the knowledge-layer thesis. Its
pre-registered success and stop conditions are in
[phase2-preregistration.md](phase2-preregistration.md).

## Runtime qualification

A release candidate is run through the tests its `.osp/surfaces.yaml`
requires on each required runtime (install through the release-lock
match) and the record lands under `.osp/qualification/`. What each test
asserts is in [runtime-distribution.md](runtime-distribution.md); the
procedure, by harness on Claude Code and by hand elsewhere, is the
[release qualification guide](release-qualification-guide.md). The
conversational tests use the prompts in the capability's `probes`
block, verbatim on every runtime.

## Behavior prompts

`docs/prompts/behavior/` holds the Claude Code acceptance tests captured
verbatim: setup, expected behaviors, pass criteria, and a results log.
They test scientific judgment on one runtime and are the seed corpus
for eval cases. Conventions: a prompt states the task and the
environment only, never the behavior under test; tests that must stay
blind copy fixtures to neutral filenames away from any documentation
that names the defects; a headless run is
`claude -p "<prompt>" --allowedTools '<list>' --max-turns <n>` and
grades the transcript plus any produced artifacts; results are logged
per file, newest first, with date, runtime, pass or fail and one line
of evidence. The workflow prompt files beside them (one per workflow
skill, slash form and one conversational phrasing) are described in
[prompts/README.md](prompts/README.md).
